# 第一部分：PRD

## 1. 产品定位

**一句话**：插上线，把 Mac 上的视频和照片推到手机，像用 Finder 一样浏览两端。

DroidBerth 是一款 macOS 应用，让用户在 Mac 与 Android 手机之间双向传输文件，**并以「Mac → Android」为主场景优化**。ADB 二进制内嵌在 app 内，用户不需要安装 Android SDK、不需要接触终端、不需要理解 ADB。

**它不是什么**：不是设备管理器，不是开发者工具，不是备份工具。范围刻意收窄（见 §4）。

## 2. 目标用户

**主用户（唯一主用户）：摄影师 / 视频创作者**

手上有大量已拍摄、已在 Mac 上整理过的视频与照片素材，需要把它们推到 Android 手机上——用于在手机上看片、给客户/同事看、装到平板或备用机上播放。

这个选择决定三件事：
- **默认交互是「推」而不是「拉」**：窗口里最高频的动作是 Mac → Android。
- **单次传输量大**：几十到几百个文件、单个文件可能上 GB。
- **素材来源常在图库里**，不在普通文件夹里（→ §18 照片图库来源）。

**次用户**：Mac + Android 双设备用户，双向零散交换文档与照片。

**明确排除**：开发者/技术用户。ADB 终端、日志流、整机备份都不做——它们会把产品拉向另一个形态。

## 3. 用户核心场景

| 场景 | 方向 | 频率 | 备注 |
|---|---|---|---|
| **推送素材到手机** | Mac → Android | **高（主场景）** | 可能来自 Finder，也可能来自照片图库 |
| **浏览设备内容** | 只读 | 中 | 确认推送到位了没、看看手机里有什么 |
| **回传文件** | Android → Mac | 中 | 手机拍的、下载的东西拿回 Mac |
| **整理设备文件** | 删除 / 重命名 / 新建文件夹 | 中 | 「放错地方了挪一下」「传错了删掉」 |
| **从照片图库推送** | Mac 照片库 → Android | 高 | 主场景的一种来源形态 |

> v1.0 的场景表把「导入照片到 Mac」列为高频第一行，方向是反的，已修正。

### 5.1 架构范围：已决定放弃 Intel（2026-10-09 确认）

v2.0（以及 §0 第 8 行）把 **universal（arm64 + x86_64）** 列为发布阻塞项。Swift 路线落地时**主动放弃了 Intel**（`0926_03` §3.5）：

- spike 实测发现 `droidberth-adb` 只有 arm64 切片，而 Xcode 默认 `ARCHS=standard` 会产出 universal 主二进制
- 结果是 **Intel Mac 上 app 能启动、sidecar 起不来**——属于「启动后静默失效」，比直接崩溃更难排查
- 两条修法中选了「放弃 Intel」（`macos/project.yml` 设 `ARCHS: arm64`），理由是目标用户（摄影师 / 视频创作者）的设备以 Apple Silicon 为主

**决策（2026-10-09）：保持放弃 Intel，v1 只发 Apple Silicon。**

- §0 第 8 行与 §28 的「universal 为发布阻塞项」**随之作废**，发布前检查清单按 arm64-only 执行
- 发布页需要**明确写出**「需要 Apple Silicon」，不能让 Intel 用户下完才发现打不开
- 若日后决定恢复 Intel 支持，**顺序不能颠倒**：先让 `macos/Scripts/build-sidecar.sh` 同时构建 `aarch64-apple-darwin` 与 `x86_64-apple-darwin` 并用 `lipo -create` 合并，**再**改 `ARCHS` —— 否则会退回「启动后静默失效」

## 6. 技术约束

### 6.1 adb 的来源（v1.0 的前提已推翻）

v1.0 §6 与 §24 写的是「ADB sidecar 必须自行编译（AOSP Soong），不得直接分发 SDK 中的 platform-tools 二进制」。**这条建立在一条不成立的前提上。**

实测证据（`vendor/` 目录）：

| 证据 | 结果 |
|---|---|
| `vendor/adb-build/` | **空目录** |
| `vendor/platform_system_core/adb/` | **不存在**（sparse checkout 未落地；顶层只有 `libcutils`/`libutils`/`rootdir` 等） |
| 全树 `CMakeLists.txt` | **0 个** |
| 全树 `Android.bp` | **15 个**（Soong） |
| 仓库里唯一的 `adb` | SDK 的 universal 18 MB 副本，**非自建** |

`scripts/build-adb.sh` 自己的 VERDICT 写着：

> A self-built adb is a **build-glue project, not a script**.

它验证的是**这条路不通**（上游没有 CMake 路径），不是通了。三个候选第三方仓库全部陈旧（2016 / 2021 / 2024），其中两个**没有任何许可证**。

**v2 的决策**：v1 使用 **SDK 的 adb**，构建时由 `macos/Scripts/build-sidecar.sh` 从 `vendor/platform-tools/adb` 暂存到 `macos/Sidecar/`。

- 已验证依赖**全部是系统库**（`otool -L` 非系统路径依赖 0 个），不构成公证障碍。
- **必须随包附 `NOTICE.txt`。**
- 许可实情：`NOTICE.txt` 声明整包 Apache-2.0；SDK 条款的再分发禁令是 **§3.4**（v1.0 引用的 §3.3 是错的），而 **§3.5 对开源许可组件有豁免**。所以「必须自建才能公开分发」这个前提本身不成立。
- **但这仍不是法律意见。** 公开发布前必须让法务确认 §3.5 的适用性。**不要写成「无风险」。**
- 自建 adb 列为「若法务否决则切换」的备选，且必须按 **build-glue 项目** 立项（自己的周期与估算），不是脚本。

### 6.2 其它约束

**通用**：

- sidecar 定位用**相对自身可执行文件**的路径，不用安装路径拼接。
- 子进程封装必须**同时抽干 stdout 和 stderr**，并带超时。
- **禁止手写 `hdiutil create`**，统一走 `scripts/env.sh` 的 `make_signed_dmg()`。
- 构建前清理输出目录里的 `rw.*.dmg`：`hdiutil` 会把未 detach 的中间卷喂回 `create`，造成产物不一致。

**应用工程（`macos/`）**：

- **构建前置**：必须先跑 `macos/Scripts/build-sidecar.sh` 把 sidecar 暂存到 `macos/Sidecar/`，否则 Xcode 的 `preBuildScript` 直接 fail。
- **架构一致性**：`ARCHS` 必须与 sidecar 的切片匹配，见 §5.1。
- **xcodegen 的 `USER` 变量**：某些 shell 环境下 `USER` 未设置会让 XcodeGen 报错且**静默不生成工程**，构建命令需显式传 `USER=$(id -un)`。
- **产物目录不止一个**：`build/Release/` 与 `build/dd/Build/Products/Release/` 是**两个独立产物目录**，构建目录不同就是不同的二进制。验证 UI 改动前先 `ps -o pid,lstart` 核对启动时间是否晚于相关源码的 mtime（`0926_03` §5.4）。
- **adb 不随仓库分发**：`macos/Sidecar/` 是 `.gitignore` 排除的暂存目录，其中 `adb` 从 `vendor/platform-tools/adb` 复制而来；体积与许可双重理由，不进版本库。

# 第二部分：产品设计文档

## 8. 设计原则

> **v2.1 说明**：四条原则的**产品意图完全保留**——像 Finder、不引入非系统视觉、每个主命令有快捷键；本次只把表述落到 SwiftUI / AppKit 的具体控件与 API（§0.1）。

### 原则一：优先系统控件，不自造系统已有之物

- **能用系统控件就用系统控件**：`NSToolbar`、`Table` / `List`、`NSOpenPanel`、`QLPreviewPanel`、右键菜单、`NSAlert`、拖拽光标与徽章——SwiftUI / AppKit 都有原生实现，不重造。
- **不引入非系统视觉**：不用自定义圆角卡片、不用非系统配色、不用非系统字体。
- **尺寸、间距、字号、控件形态照 HIG**，不自创。宁可「平庸但正确」，不要「有设计感但不对」。
- **判据**：把窗口截图和 Finder 并排放在一起，用户不应看出差别。

### 原则二：窗口结构走系统标准形态

用 SwiftUI 的 `WindowGroup` + `.toolbar` / `ToolbarItem` 表达工具栏，`HSplitView`（或 `NavigationSplitView`）表达双栏，用 `defaultSize` 与 `frame(minWidth:minHeight:)` 约束尺寸。**不手工预留交通灯区域**——窗口装饰由系统管理。

### 原则三：材质用原生 Material API

工具栏、窗格头、传输面板可用材质；表格、列表、文件内容区不使用。

- 用 `.regularMaterial` / `.bar` / `.thinMaterial` 等 SwiftUI 原生材质，**自动**响应窗口失焦降饱和与「降低透明度」辅助功能设置。
- 若某处原生材质效果不符预期，**优先改用系统色纯色**，不要用自绘渐变硬仿——仿不出来的部分比不做更伤「原生感」。

### 原则四：每个主命令有快捷键，且不覆盖系统语义

见 §22。注意：**⌘C / ⌘V 在本产品里必须被占用**（跨栏 = 传输），v1.0 把它们列为「不可占用」是错的。

## 9. 信息架构：双栏

```
┌──────────────────────────────────────────────────────────────────────┐
│  [标题栏与红绿灯由系统统一管理]                                       │
├──────────────────────────────────────────────────────────────────────┤
│  [列表|分栏|网格]   [⇄ 交换两侧]              [搜索]        [⋯]        │
├───────────────────────────────┬──────────────────────────────────────┤
│ 这台 Mac            [来源 ▾]  │ Pixel 8                   [位置 ▾]    │
│ ‹ ›  ~/Movies/2026-09        │ ‹ ›  内部存储/DCIM                   │
│───────────────────────────────┼──────────────────────────────────────┤
│  📁 剪辑输出                  │  📁 Camera                           │
│  🎬 A001_final.mp4  4.2 GB    │  🖼 IMG_2041.jpg    3.1 MB           │
│  🎬 A002_final.mp4  3.8 GB    │  🖼 IMG_2042.jpg    2.9 MB           │
│  🖼 cover.jpg       1.2 MB    │  ...                                 │
│                               │                                      │
├───────────────────────────────┴──────────────────────────────────────┤
```

**为什么是双栏而不是单栏**：主场景是「推」。双栏让「从 Mac 挑 → 拖到设备」在一次视线内完成，不需要在 Finder 和 app 之间来回切窗口。这也是 macOS 上双栏文件管理器的既有约定（ForkLift / Commander One / Path Finder）。

**代价（必须承认）**：每个窗格都要有完整的列表 / 分栏 / 网格三种视图，UI 工作量相对单栏翻倍。

- 左：返回 / 前进箭头（与 Finder 一致）

> **实现形态（Swift 原生，v2.1）**：工具栏由 SwiftUI `.toolbar` + `ToolbarItem` 表达——`ToolbarItem(placement: .navigation)` 放设备菜单，`.principal` 放 ⇄，`.primaryAction` 放主命令。窗格头是自绘的 `HStack`（标题 + 面包屑 + 来源切换器）。**不需要交通灯预留区**——窗口装饰由系统管理（§8 原则二）。

> **实现现状（2026-10-09）**：聚焦态**已达标**（Phase 1.4：窗格头 `fontWeight` 加重 + 系统色 2pt 描边 + 6% 背景色，形状与字重两重区分，不只靠颜色）。工具栏已按 Phase 2.1 重构：⇄ 居中、搜索框、⋯ 溢出菜单、上传/下载常驻。**两处刻意偏离**：① 上传 / 下载没有按原文收进 ⋯ —— 它们是本产品的核心动作，藏进菜单是净损失；② 视图切换分段控件**延后到 Phase 3**，因为分栏与网格视图本身是 Phase 3 内容，先摆一个只有一项可用的分段控件属于**假可用**。设置按钮从工具栏移到 app 菜单并接上 ⌘,（放两处只会让人犹豫）。
>
> **可见侧边栏：不做（2026-10-09）**。原计划用 `NavigationSplitView` 做常驻侧边栏，评估后放弃：这是一个双栏传输工具，第三栏会**永久**吃掉横向空间（窗口最小宽 900pt，减去侧边栏后每栏只剩 ~340pt），而「位置」是偶发动作。真正的痛点是「回到上次传的那个项目文件夹」，所以改为**「位置」弹窗**：把「最近使用」（持久化，最多 8 项）排在固定位置之前。

**预览窗格（2026-10-10，Phase 3.5）**

| 项 | 决定 |
|---|---|
| 落位 | **窗口右缘**（Finder 的约定），只占内容区高度、不侵入底部传输面板 |
| 显示谁 | **聚焦窗格**的选中项。头部写明来源（这台 Mac / 照片图库 / 设备名），避免被误当成设备栏的附属 |
| 开关 | **默认关**，⇧⌘P 切换，状态跨启动保留 |

| 内容 | 缩略图 + 名称 + 种类 / 大小 / 修改日期 + 完整路径（可选中复制）+ 按来源给**一个**传输按钮 |

>
> **顺带确立的一条交互规则（2026-10-10）**：**在哪个窗格改选择，焦点就落在哪个窗格**（与 Finder 一致）。此前点选行不设焦点，于是「点完设备栏再按 ⌘⌫」会因为菜单项按旧焦点被禁用而什么都不发生 —— 一个静默的错。预览窗格、⌘C/⌘V、⌘⌫ 都以聚焦窗格为准，这条规则把它们对齐了。

> 实现提示（Swift 原生）：用 `NSViewRepresentable` 包装 AppKit 的 `NSBrowser`，**不要自绘复刻**。列宽、列间距、选中态、滚动位置保持全部交给 `NSBrowser`，天然对齐 HIG。

**13.2 实现说明（2026-10-10，Phase 3.2）**

- 落地形态：`Views/EntryColumns.swift`，**item-based** 的 `NSBrowser`。列宽、滚动、选中态全部由 AppKit 负责，未自绘。
- **子项是异步填的**：`NSBrowser` 的 delegate 是同步接口，而设备端列目录要走一次 `adb shell ls` 子进程 —— 同步等它会把主线程冻住。delegate 只读缓存，未命中就返回 0 并起异步加载，加载完 `reloadColumn` 补行。本地目录走同一条路径，避免两套行为。
- **选择变化没有通知可监听**：`NSBrowser` 只发了「列宽配置变化」的通知，选中态得靠 delegate 的 `selectionIndexesForProposedSelection`（item-based 专用）接。
- **根与「列里点到的目录」是两件事**：前者是 `localDirectory` / `remoteDirectory`（也是列表 / 网格显示的目录），后者是 `localColumnDirectory` / `remoteColumnDirectory`。根变了才 `loadColumnZero`，列内点选只更新后者 —— 否则每点一下就整体回到第一列。
- **路径栏**：分栏模式下顶栏不再显示面包屑，改为窗格**底部**一条可点的路径栏（列表 / 网格仍用顶栏面包屑）。
- **⚠️ 未验证**：列视图的一切运行时行为（铺列、异步补行、单选、双击预览、底部路径栏）；以及 `willDisplayCell` 在 item-based 浏览器里是否被调用 —— 行内的类型图标依赖它，不调用则退化为纯文本行（功能不受影响）。
- **照片图库回退成列表**：图库只有相簿一层、没有目录层级，列视图对它没有意义。

### 13.3 网格视图

- 缩略图网格，适合素材浏览
- **缩略图只拉取文件头**（不下载完整文件）；图片取前 64 KB，视频取容器头
- ⌘+ / ⌘- 调整图标大小
- 缩略图生成失败时显示类型图标，不留空白

> **实现现状（2026-10-10）**：**13.1 已实现**（Phase 1.1 + 2.4 + **Phase 4 补上重命名**）：四列齐全、列头点击排序（名称用 Finder 的本地化比较，文件夹优先且可在设置里关）、右键菜单（含「重命名…」）、多选、拖拽。
> **13.3 已实现**（Phase 3.1）：`LazyVGrid` 网格 + 每格缩略图 + ⌘+ / ⌘- 调整图标尺寸 + 生成失败回退类型图标。缩略图落地方式见下方「实现说明」。
> **13.2 已实现**（Phase 3.2）：`NSBrowser` 分栏 + 底部路径栏。实现说明见 §13.2。
> **§13 三种视图至此齐全**，且形态**按窗格独立**（`AppSettings.macViewMode` / `deviceViewMode`）。

**13.3 实现说明（2026-10-10）**

- **远端取头**：`adb exec-out` + 设备侧 `dd if=<path> bs=1024 count=64`，取前 64 KB。**必须用 `exec-out` 而不是 `shell`** —— `adb shell` 的 stdout 走 pty，会把二进制里的 `\n` 翻译成 `\r\n`，图片头当场损坏。
- **生成**：本地文件直接把 URL 交给 `QLThumbnailGenerator`；远端先落成临时文件再交给它。生成尺寸固定 512 px，一套缩略图服务所有图标档位。
- **回退**：取头失败 / 解码失败 / 类型不在图片·视频范围内，一律显示类型图标，不留空白。
- **⚠️ 未验证**：**截断数据的可解码性没有真机验证**。JPEG 通常能在缺 EOI 的情况下解出部分图像，但 HEIC / 视频容器（尤其 `moov` 在文件尾的 MP4）很可能解不出来 ⇒ 表现为回退类型图标。选项「一律拉完整文件」被明确拒绝（PRD §23），因此这一项的成品率要等真机实测才能定论。
- 现状：三种视图（列表 / 分栏 / 网格）已全部落地，工具栏分段控件与 ⌘1/⌘2/⌘3 齐了。

## 14. 传输面板

跨两栏宽度，位于窗口底部。无任务时隐藏，有任务时自动展开，可手动固定。

- 每行一个任务：方向图标（⬆ / ⬇）、文件名、进度条、速度、剩余时间、取消按钮（hover 时显示）
- 折叠态为单行摘要：「3 个传输中 · 2 个等待 · 1 个失败」
- **不用模态对话框展示进度**——传输必须非阻塞
- 失败任务整行用系统警示色标出，并提供「重试」与「查看原因」

> **实现现状（2026-10-09）**：**已实现**（Phase 2.3）。速度与剩余时间来自 `adb` 的进度解析（`ProgressParser`）；失败行常驻「重试」与「查看原因」，**不藏在 hover 后面**——失败需要被看见。折叠 / 自动展开 / 固定（pin）均已实现。
> **已知边界**：速度与 ETA 只在 `adb` 输出可解析的进度时出现；设备端写入卡住而没有输出时，界面会停在最后一个百分比（这是 `adb` 侧的限制，不是 UI 缺陷）。

## 15. 传输默认约定

这三条是最常被踩的默认值，必须明确。

### 15.1 落点分流（设备窗格当前目录不是目标时）

| 文件类型 | 默认目标 |
|---|---|
| 视频（mp4 / mov / mkv / avi / webm） | `Movies/` |
| 图片（jpg / png / heic / gif / webp / raw） | `DCIM/` |
| 其它 | `Download/` |

**设置里可改**，也可整体关掉改为「一律落到当前目录」。

> 说明：`DCIM` 语义上是「相机」目录，把用户导入的图片放进去略有语义偏差；但它是相册扫描最稳的目录。若实测发现 `Pictures/` 同样能被相册正确索引，应改为 `Pictures/`。

### 15.2 记住上次

按**设备序列号**记住该设备上次用过的目标目录。**优先级高于分流规则**——用户上次明确去过哪，下次默认还去那。

### 15.3 重名冲突

- **默认：保留两者**，自动加 ` (1)`、` (2)` 后缀。与 Finder 行为一致。
- **绝不静默覆盖。**
- **传输前批量预检**：开始前一次性列出目标目录内容，把所有冲突判定完，而不是传到一半才发现。冲突数量 > 5 时在传输面板上给一条汇总提示（「其中 12 个文件已存在，将保留两者」）。

## 16. 设备端写操作

| 操作 | 行为 | 保护 |
|---|---|---|
| 新建文件夹 | 设备端 `mkdir` | 重名时提示，不静默改名 |
| 重命名 | 设备端 `mv` | 重名时提示 |
| 删除 | 设备端 `rm` | **二次确认**，文案必须明确「此操作不可撤销」；多选时列出文件数与总大小 |

**为什么删除不做回收站**：设备端没有标准回收站；自己建隐藏目录会污染用户设备、且用户拔线后看不见它。v1 用「二次确认 + 明确文案」，把「设备端回收站」列为 P2 候选。

**待验证**：设备端文件名的合法字符集。`/sdcard` 通常是 FUSE 层，底层 ext4/f2fs 允许大多数字符，但 MediaStore 可能不索引某些字符，FAT32 格式的 SD 卡则明确禁止 `: * ? " < > |`。重命名校验规则需要实测后确定。

**16 实现现状（2026-10-10，Phase 4）**

| 操作 | 状态 |
|---|---|
| 新建文件夹 | 已实现（Phase 2.4） |
| 重命名 | **已实现**：右键「重命名…」→ 预填原名的输入框。校验抽成纯函数 `AppModel.validateRemoteName`（空 / `.` / `..` / 含 `/` / 超 255 字符），名称不合法时「重命名」按钮直接禁用 |
| 删除 | 已实现（二次确认） |

> **冲突策略是「拒绝」而不是「覆盖」**：同目录已有同名时直接拒绝并说明，不调 `mv` 的默认覆盖行为。设备端覆盖不可逆，且没有回收站。
>
> 上面「待验证」的**文件名合法字符集仍未实测** —— 当前校验只挡住了必然非法的情况（`/`、空、`.`、`..`、超长）。FAT32 的 `: * ? " < > |` 与 MediaStore 的索引限制都要等真机才能定规则。

## 17. 连接与引导

### 17.1 USB（默认通道）

- 插入后轮询 `adb devices -l`：活跃时 1 秒间隔，空闲 5 秒后退避到 3 秒
- **未授权**（`unauthorized`）时显示引导卡片：手机上的「允许 USB 调试？」图示 + 「勾选『始终允许』再点确定」+ 「已完成，重新检测」按钮
- **厂商差异**：小米 / OPPO / vivo 的开发者选项流程含额外风险提示与等待步骤，引导卡片按检测到的品牌显示对应图文

### 17.2 无线（静默双通道，P0）

**核心原则：用户不应该看见「连接方式」这个概念，只应该看见「设备在不在」。**

- 按设备序列号记住上次的 `IP:5555`
- USB 在线时**一律走 USB**（更快）
- USB 拔出后**自动尝试** `adb connect <ip>:5555`，**失败不弹错误**
- 失败时只在设备卡片上显示一个**可点的状态点**（灰点 + 「无线未连接」），点开才展开原因
- 无线连接成功后，设备窗格头显示 Wi-Fi 图标

**首次启用无线的引导**（需要 USB 激活一次）：
1. 设备已通过 USB 连接
2. 用户在 Device 菜单选「启用无线连接」
3. 执行 `adb tcpip 5555`
4. 读取设备 IP（`adb shell ip addr show wlan0`）
5. 提示可以拔线
6. 执行 `adb connect <ip>:5555`

**已知限制，必须做成引导而不是报错**：手机重启后端口失效，需要重新插线激活一次。检测到「记住的无线设备连不上且当前无 USB」时，显示「需要插线重新激活一次」的引导卡片。

**5037 端口冲突**：启动时检测四种状态（空闲 / 是我们自己的 adb / 是别的 adb / 是非 adb 进程）。是「别的 adb」时提示用户——版本不一致会静默改变行为。

## 18. 素材来源：Finder + 照片图库

主用户的素材常常在照片图库里，不在普通文件夹里。

### 18.1 技术约束（实测结论）

- 第三方 app **不能直读**照片图库。必须走 Photos framework，并在「系统设置 > 隐私与安全性 > 照片」里获得授权。
- **没有任何免授权路径。**
- 需要在 Info.plist 里提供 `NSPhotoLibraryUsageDescription`。
- 导出是**异步**的（`requestExportSession` / `requestImageData`），必须有进度与取消。

### 18.2 设计

- Mac 窗格头的「来源」下拉可切到「照片图库」
- 浏览维度：相册 / 时间（年-月-日）/ 媒体类型（照片 / 视频）
- 选中后拖到设备窗格 = 先导出到临时目录再推送。**UI 上必须把「导出」和「推送」两段进度分开显示**，否则用户会以为卡住了
- 权限被拒时的降级路径：显示一条可点的提示「去系统设置开启照片访问」，同时**产品其余功能完全不受影响**（不能因为照片权限被拒就挡住普通文件传输）

## 19. 媒体入库（MediaStore）—— 最高风险项

### 19.1 问题

`adb push` 是把文件写到文件系统，**不经过 MediaStore**。而 Android 的相册 / 图库读的是 MediaStore 索引，不是文件系统的实时视图。**如果索引不更新，用户推过去的文件在相册里看不见——产品在核心任务上就失败了。**

### 19.2 证据状态（不要写成「已知缺陷」）

| 结论 | 强度 |
|---|---|
| `MEDIA_SCANNER_SCAN_FILE` 广播在 **API 29 已废弃**（官方原文：应改为直接插入 MediaStore，插入后自动扫描） | **已确证** |
| Android 11+ 起 MediaProvider 走 FUSE，AOSP 表述为「文件系统与数据库保持一致」 | 已确证，但**未明确 `adb push` 这个场景** |
| 因此 11+ 上可能**自动入库**，旧版本上很可能**看不到** | **推断** —— 必须真机逐版本实测 |
| 没有任何来源能确认某条扫描命令在 **Android 10–16 全版本**有效 | **未查到** |

### 19.3 v1 策略

1. **以新 API 为基准**：优先使用 MediaStore 的插入/扫描路径，而不是已废弃的广播。
2. **按 Android 版本选择命令**，并在传输完成后对每个已传文件触发一次扫描。
3. **全部命令标为待验证**，并在**至少 3 个 Android 版本**（建议 10 / 13 / 15）上实测。
4. **兜底引导**：扫描失败时，在传输完成卡片上给一条明确、可操作、不甩锅的指引——「在手机上打开相册，下拉刷新；若仍看不到，重启手机后即可出现」。
5. **不要静默失败。** 媒体入库失败必须在 UI 上可见，否则用户会在几小时后才发现相册是空的，而那时已经找不到原因。

### 19.4 如果实测证明全版本都无法可靠入库

那说明「内嵌 adb + 零安装」这条技术路线与「推送后立刻能在相册看到」这个产品承诺**存在根本冲突**。届时需要在三件事之间做取舍：配一个 Android companion app / 改用 MediaStore API 通道 / 修改产品承诺的措辞。**这个取舍留到实测之后做，现在不预判。**

## 20. 大文件与中断代价

**`adb push` 不支持断点续传**（`SYNC_CMD_WRITE` 无 offset；中断即清理临时文件、必须全量重传）。这条的置信度为**中等**（来源非官方），但设计上按「成立」处理。

| 措施 | 说明 |
|---|---|
| 传输前检查目标分区剩余空间 | `adb shell df`，空间不足直接拒绝开始，不留到传一半才失败 |
| 大文件（> 1 GB）排在队首并**独占通道** | 减少被小文件插队导致的资源争抢 |
| 进度显示「已传 / 总量」的绝对数值 | 不能只给百分比 |
| 失败时明确告知重传代价 | 「已传输 6.2 GB，重试将从 0 开始」——不能让用户以为会续传 |
| 一键重试 | 保留原目标路径与重名策略 |

**不做分片续传**（绕过 `adb push` 用 `adb shell` + dd 逐块写）。理由：要自己实现校验与进度记账，且会明显拖慢速度，收益不足以进 v1。

### ⌘C / ⌘V 的正确语义（修正 v1.0）

v1.0 把 ⌘C / ⌘V 列为「保留给文本和列表的默认行为，不覆盖」。**这在文件管理器里是错的。**

在 Finder 里，选中文件后 ⌘C、切到另一个窗口 ⌘V，就是拷贝文件。双栏文件管理器里，这个动作的自然含义就是**跨栏传输**：

- Mac 栏选中 → ⌘C → 设备栏 ⌘V = **上传**
- 设备栏选中 → ⌘C → Mac 栏 ⌘V = **下载**
- 同栏内 ⌘C → ⌘V = 在同一侧复制（设备侧走 `cp`；Mac 侧走 Finder 的拷贝语义）

**例外**：焦点在文本输入框（重命名、新建文件夹、搜索）时，⌘C / ⌘V 恢复为文本编辑语义。这是标准的 responder chain 行为，必须正确处理。

### 不覆盖的系统快捷键

⌘Z / ⇧⌘Z（撤销）、⌘A、⌘F（搜索聚焦）、⌘W、⌘Q、⌘H、⌃⌘F。

**关于撤销**：设备端文件系统操作（删除 / 重命名 / 移动）**不可撤销**——设备端没有回收站。⌘Z 仅作用于文本输入。这必须在删除确认文案里说清楚，不能给用户「反正能撤销」的错觉。

## 23. Quick Look

### 目标形态

按空格键，**就地**弹出 Quick Look 面板预览选中的文件。

### 实现路径（Swift 原生，v2.1）

- 用 SwiftUI 的 `.quickLookPreview(_:)`，底层即系统 `QLPreviewPanel`，**天然就地**，不需要任何插件包装。
- **兜底**：`qlmanage -p` 只作为降级方案保留——它是**另开窗口**，不是就地预览，仅在 `.quickLookPreview` 不可用时才考虑。
- **导入前提（2026-10-09 实测）**：`.quickLookPreview(_:)` 不在 `SwiftUI` 模块里，它由 `QuickLook` + `SwiftUI` 的 cross-import overlay（`_QuickLook_SwiftUI`）提供。只写 `import SwiftUI` 会报 `has no member 'quickLookPreview'`，**必须同时 `import QuickLook`**。该 API 的实际可用性标注是 macOS 11.0+，比本节原先写的 14.0+ 更宽。

### 约束

- 预览需要本地文件。远端文件的流程：选中 → 拉取到 `$TMPDIR/DroidBerth/preview/` → 预览 → 关闭后清理。
- **大文件保护**：> 200 MB 的文件按空格时先确认（「该文件 4.2 GB，预览需要先下载到本机」），不要静默开始下载。
- **优化**：只在用户真的按空格时才拉文件。Quick Look **不能**用「只拉文件头」代替 —— 预览器要能解码整个文件，所以预览一律拉完整文件（大文件有上方确认保护）。§13.3 的网格缩略图另有一条「只拉 64 KB 头」的通道，但那条通道**只服务缩略图**，且其成品率未在真机验证（见 §13.3 实现说明）。

> **实现现状（2026-10-09）**：已实现，编译通过、**运行时行为待人工验收**。本地文件就地预览；远端文件先 `adb pull` 到 `$TMPDIR/DroidBerth/preview/<UUID>/<原名>` 再预览，> 200 MB 弹确认。**未做**的两点：① 「图片只拉文件头生成缩略图」——当前一律拉完整文件，因为 Android 侧没有稳定的远端缩略图通道，留待 Phase 3 与网格视图一起解决；② 照片图库条目不参与预览（需先导出成文件）。另：多选时按空格不预览，事件交还系统。见 `1009_01_uiux-revamp-plan.md` Phase 1.3 / §2.6。

## 24. 拖拽

遵循 macOS 约定：**同一容器内拖拽 = 移动；跨容器拖拽 = 拷贝**。

| 拖拽方向 | 行为 |
|---|---|
| Finder → 窗口（任意位置） | 上传到设备窗格当前目录 |
| Mac 窗格 → 设备窗格 | 上传 |
| 设备窗格 → Mac 窗格 | 下载 |
| 设备窗格 → Finder | 下载到 Finder 目标位置 |
| 设备窗格内部 | 设备端移动（`mv`） |
| 设备 A 窗格 → 设备 B 窗格（P1） | 经 Mac 中转 |

- 拖拽进入目标区域时高亮
- 释放后任务进入传输面板，**不弹任何对话框**
- 拖拽多选时显示文件数量徽章
- **不可拖拽的情况要有明确反馈**：`Android/data`、`Android/obb` 不可写入，拖上去应显示禁止光标而不是静默失败

**24 实现现状（2026-10-10）**

| 方向 | 状态 |
|---|---|
| Finder → 窗口 / Mac 窗格 → 设备窗格 | 已实现（Phase 1.1） |
| 设备窗格 → Mac 窗格 | 已实现（Phase 1.1） |
| 设备窗格内部 = 设备端移动 | **Phase 4 已实现**：拖到设备窗格 = 移进该窗格当前目录；用 ⌘X/⌘V 也可以 |
| 设备窗格 → Finder 拖出 | **未实现**（需 `NSFilePromiseProvider`） |
| Mac 窗格内部 | **明确不做** —— 本地文件的移动交给 Finder |

> **移动的冲突策略是「整批拒绝」而不是覆盖**：目标目录里已有同名时，一个都不移动并报出冲突名，不做静默覆盖。`mv` 默认会覆盖，而覆盖的是用户手机上的数据。

| 6 | 文件系统操作不可撤销（⌘Z 只作用于文本） | 设备端无回收站；给用户「能撤销」的错觉比不给更危险 |
| 7 | 删除用二次确认，不做设备端回收站 | 见 §16 |
| 8 | 不沿用 v1.0 的工期估算 | 范围已显著扩大，旧估算不可比 |
| 9 | DMG 只由公证脚本产出，打包时不全量输出 | 避免出现两个来源不同、签名状态不同的 DMG |
| 10 | 图片默认落 `DCIM/` 而非 `Pictures/` | 你在第 4 轮选了 `DCIM/`；但若实测证明 `Pictures/` 同样被正确索引，应改过去 |
| 11 | v2.1 只对齐**实现约束**，不改**产品意图** | 你的要求是「先更新 PRD，再修正 UX」；产品意图与实现细节无关 |
| 12 | 架构范围（Intel 支持）先标为**待决策**，后于 2026-10-09 由用户确认**放弃 Intel** | 这是产品决策，不应由文档单方面改写（§5.1） |
| 13 | v2.1 未重写 §22 / §24 / §25 的正文，只在其内标注实现现状 | 这三节的**产品要求仍然有效**，要改的是「有没有做到」而不是「要不要做」 |

---

**总结**：v2.0 把验证 demo 已走通的技术链路（签名、公证、ADB 嵌入、诊断机制）转化为产品规划，并修正了 v1.0 的六处实质错误——**方向反了、形态错了、adb 来源建立在一个未验证的前提上、设计原则停在口号层、Quick Look 方案是降级的、⌘C/⌘V 的语义判断是错的**。

主场景已明确为「把 Mac 上的素材推到手机」，因此双栏是正确形态、照片图库是必需来源、而**媒体入库是整份文档里最大的未知**——它必须在 Phase 3 之前实测，因为它可能推翻的不只是一个功能，而是「内嵌 adb + 零安装」这条路线能否支撑产品承诺。

**v2.1 总结**：v2.1 把 v2.0 里所有抽象的**实现约束**对齐到 SwiftUI / AppKit 的具体落点——§8 三条原则、§9 / §10 窗口结构、§13.2 分栏实现、§21 外观、§23 Quick Look、§5 内存基线，并新增 §4.3 实现现状、§5.1 架构范围、§26 身份字段。**产品意图未改一字。**

当前最大的**体感**差距在交互层：拖拽（§24）、⌘C/⌘V 跨栏（§22）、Quick Look（§23）、分栏 / 网格视图（§13）、无障碍（§25）均未实现。产品因此更像「一个能传文件的表格页」而不是文件管理器——这正是「交互过时」的来源。差距清单与分阶段改造方案见 `1009_01_uiux-revamp-plan.md`。
