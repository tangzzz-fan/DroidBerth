图标体系与引导插图

一份可直接落地的图标规格：文件类型如何映射到 SF Symbols、双栏如何区分来源、未授权时如何引导用户，以及四类空态该怎么写。所有图形只用系统两条路径实现——SF Symbols 与 NSWorkspace，不新增任何自绘位图。

设计原则

下面五条是这份文档里所有判断的依据。第 1 块里每一个"不值得新增"的结论，都可以回溯到其中的第 3 条。

  • 形状承担类型，颜色承担来源，文字承担精度。图标永远不是唯一的信息载体（§8-3）：种类、大小、日期三列必须能脱离图标独立读懂这一行。
  • 只有两条实现路径。NSWorkspace 提供系统彩色文件图标，SF Symbols 提供单色矢量符号。粗细、圆角、配色全部落在系统语义里，不做自定义图标风格。
  • 16pt 下三秒可辨。两个符号若需要凑近才能分辨，就合并成一个——合并是默认答案，新增需要理由。判据见 1.4。
  • 图标不承诺运行时事实。"这个文件手机能不能打开""这个包能不能装"，由禁用态和文案回答，不由图标回答。
  • 一套符号名，两种呈现。同一个类型在本机与设备两侧用同一个 symbol 名，差别只在彩色与单色。
01

文件类型图标体系

列表视图名称列行首的 16pt 图标，同时也是网格视图缩略图生成失败时的回退图形（回退时用同一 symbol 的 64pt 实例，不要放大小尺寸位图）。

1.1 两条路径，各管一栏

左栏的文件真实存在于这台 Mac 上，交给 NSWorkspace.shared.icon(forFile:)：系统会给出 Finder 里那个彩色图标，装了 Office 就自动变成 Word 图标，我们零维护。右栏的条目是 adb 列出来的，本机并没有这个文件，路径返回的只会是通用文稿图标——所以右栏必须由我们自己的"扩展名 → SF Symbol"映射表接管。这张表就是 1.2。

// 左栏：系统彩色图标，零维护
let icon = NSWorkspace.shared.icon(forFile: url.path)
icon.size = NSSize(width: 16, height: 16)

// 右栏：设备侧条目，本机不存在，只能自己映射
Image(systemName: symbolFor(ext: "mp4"))   // → "film"
  .font(.system(size: 16))
  .foregroundStyle(.secondary)             // 选中行内改为 .white

读法：表中的 左 一律是 NSWorkspace 自动结果；右 是右栏（设备侧）要写进代码的 symbol 名。

1.4 一条判据，决定要不要新增符号

一个类型值得拥有独立符号，当且仅当三条同时成立：

  • (a) 用户会对它做出不同的动作。dmg 是"挂载"，zip 是"解压"；替身是"跳到别处"，普通文件是"打开自己"。动作不同，才值得一个不同的图形。
  • (b) 它在目标用户的文件里高频出现。DroidBerth 的用户是会用 adb 的人——代码与配置文件的出现频率远高于普通用户，而 pptx 在手机侧几乎不出现。
  • (c) SF Symbols 里有一个现成的、16pt 下与已有符号可辨的符号。这一条不过，就合并；不要为了凑一个图标去自绘。

判据 (c) 是最常被忽略的一条：找不到合适的系统符号，正确做法是继续用通用文稿图标，而不是画一个。

1.5 必须新增映射：结论清单

净增 3 个符号

现有实现覆盖 folder / 视频 / 图片 / 音频 / 压缩包 / apk / pdf / 文本 共 8 个专用符号，加 1 个通用文稿兜底。新增的只有三个：tablecells（表格）、opticaldisc（磁盘映像）、chevron.left.forwardslash.chevron.right（代码/配置）。其余你列出的类型全部并入现有符号——这是刻意的克制，理由见 B 组。

另外，把左栏从"自维护映射表"改回 NSWorkspace 之后，替身与全部办公文档类型都自动获得了正确的彩色图标，这张表就只需要维护右栏一份。

A · 值得单独给符号
  • 表格 tablecells：对用户是"里面有格子、要横向看的数据"，与文稿的动作不同；网格形在 16pt 下与三行文本可辨。
  • 磁盘映像 opticaldisc：dmg / iso 的动作是"挂载成一个卷"，不是"解压"；且 dmg 在 Mac 上高频到近乎系统文件。
  • 代码 / 配置 chevron.left.forwardslash.chevron.right：目标用户就是开发者，json / plist / sh 在 adb 相关目录里高频；且 </> 形状在 16pt 下辨识度极高，成本几乎为零。
B · 不值得单独给符号
  • B-1 全部图片格式（heic / webp / tif / avif…）：对用户是同一件事——一张照片。heic 与 jpg 给不同图标是纯噪声。
  • B-2 RAW 格式（dng / cr2 / nef / arw）：能不能推、手机能不能开，取决于接收端解码能力，是运行时才知道的事。要提醒就用文字或角标，不要换图标。
  • B-3 全部视频 / 音频容器：容器与编码差异对用户不可见，flac 与 mp3 的差别是音质不是类别。
  • B-4 无扩展名 vs 未知类型：两者对用户的含义都是"我不知道这是什么"，共用一个 doc，靠种类列写「无扩展名」/「未知」区分。
  • B-5 演示文稿（ppt / pptx / key）：设备侧几乎不出现；而且找不到一个既准确、又在 16pt 下与 tablecells 可辨的系统符号——判据 (c) 不过，合并。
  • B-6 办公文稿（doc / docx / pages）：左栏本来就有 NSWorkspace 给的彩色应用图标可以区分，右栏再造一个形状收益不抵认知成本。
  • B-7 aab / ipa / exe：与 apk 共用 shippingbox。对 Mac 用户这四个是同一件事——给别的设备装东西的包。不要用图标表达"这个不能推到 Android"，那是禁用态与文案的职责（§8-3）。

1.6 已知冲突

  • ts：既是 MPEG 传输流（视频）也是 TypeScript 源文件。按视频归类，与 macOS 自身的关联一致（QuickTime / VLC 抢注 .ts）。如果以后收到 TypeScript 用户的反馈，再按"同目录存在 package.json 或 tsconfig.json 时判为代码"处理——但不要现在就加这种启发式。
  • key：Keynote 文稿与私钥共用扩展名。都归入 doc.text，可接受——私钥文件通常带 .pem 或没有扩展名。
  • gz / raw：可能是单文件压缩或任意原始数据。落在同一个符号下不影响任何用户动作。
  • 匹配必须是完整扩展名精确匹配，不能截前缀——否则 m4a 会被 m4 吞掉。

03

USB 授权引导卡片

设备插上但未授权时，设备栏不能只留一行灰字——用户此刻正盯着手机，而不是盯着 Mac。卡片按 300pt 宽设计，以便嵌进 340pt 的窗格；正文最小 11pt。

3.1 什么时候出现

触发条件是 adb devices 里这台设备的状态为 unauthorized——即手机端尚未确认这台 Mac 的 RSA 指纹。用户点「允许」之后状态会变成 device；点「重新检测」等价于重跑一次 adb devices。

还有一个必须覆盖的死角：如果手机端根本不再弹窗（上次误点了「拒绝」，或本机的 adbkey 被重新生成过），状态会长久停在 unauthorized。这时卡片底部的品牌变体位要能接住——引导用户去开发者选项执行「撤销 USB 调试授权」，再重新插拔。

四类空态

  • 主文案里要带上产生空态的那个具体值。搜索空态写「没有找到与『合同』匹配的文件」，比「无搜索结果」多给了一条"我搜的是什么"的确认信息。
  • 动作按钮的标签自适应。第 4 类的按钮在只有搜索词时写「清除搜索词」，只有类型筛选时写「清除类型筛选」，两者都有时写「全部清除」——始终只有一个按钮，但它清除的正是用户当前的阻碍。
  • 第 3 类不要用任何警示色或感叹号。空文件夹是正常状态，不是错误。它也不该有主按钮——把一个中性状态做成操作入口，会让人以为出了问题。
  • 第 2 类必须说清"其余功能不受影响"。权限被拒最坏的后果不是少了照片，而是用户以为整个 App 废了。
