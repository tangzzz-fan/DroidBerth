# MAS（沙盒版）视觉验收 —— 2026-10-12

**第一次真的看到界面。** 此前 README 把「交互层未验收」整块挂在人眼上，依据是「本机无法截图」——
2026-10-12 查明那句话不准确：`screencapture` 在、按窗口截图也通，**缺的只是「屏幕录制」权限**。
权限到位后，这块可以从「只能人眼」变成**机器可读**。

## 方法与前提

| 工具 | 拿到什么 | 要什么权限 |
| --- | --- | --- |
| `scripts/ui-shot.sh` | 该窗口的**像素**（按窗口 id 只抓一个窗口，不抓整屏） | 屏幕录制 |
| `scripts/ui-report.sh` | 该进程的 **UI 树**（角色 / 标题 / 描述 / 值 / 是否可按下） | 辅助功能 |

两者互补：**像素能看「长什么样」，UI 树才能判「数字对不对」**。本次两者都跑了。

`03-sandboxed-mas.png` / `04-sandboxed-mas.ax.txt`（沙盒版）。同一份源码，同一次会话。

环境：macOS 27.0.1 · `Release-MAS` 配置 · Apple Distribution 身份（同时验过 ad-hoc）·
设备为模拟器 `Pixel_10`。

## F1（新发现）沙盒版**开局就站在自己的容器里**

左栏路径栏实测（AX 树）：`/ ▸ Users ▸ tango ▸ Library ▸ Containers ▸ dev.tango.droidberth ▸ Data`。

用户第一次打开 app，看到的是**他自己容器的内容**（`Documents` / `Library` / `SystemData` / `tmp`
加五个符号链接），而不是他的家目录。这既是体验问题，也是**信任问题** ——
一个文件传输工具开局给你看 `Containers` 里的东西，很难解释。

⇒ 这条把 `docs/1011_04` §2.1（Guideline 2.5.2）的代价**从纸面变成了画面**：
**E7（首次运行的授权引导）不是「可做可不做的优化」，是 MAS 版的必需件。**

**已修（同日）**：起始目录改成**真实 `~/Downloads`**（有 `files.downloads.read-write`），
并且 `LocalFileSystem.list()` 现在拒绝列出容器内部路径。修完实测：开局落在
`/ Users tango Downloads`，列出 6 项**用户的真实文件**（`.dmg` / `.JPG` …）。

## F2（新发现）沙盒下**符号链接被显示成「文稿」，还带一个假的大小**

实测行（AX 树，沙盒版）：

```
Desktop    文稿   19 B    |  Downloads  文稿  21 B  |  Movies  文稿  18 B
Music      文稿   17 B    |  Pictures   文稿  20 B
```

而同一屏里的**真目录**显示正常：`Documents 文件夹 —`、`Library 文件夹 —`。

原因在显示层：`LocalEntry.kindLabel` 只看 `isDirectory`，而沙盒下 `isDirectoryKey` **不跟随符号链接**
⇒ 那五项落进「按扩展名判种类」的分支，没有扩展名 ⇒ 「文稿」。
大小那一列同理：读到的是**符号链接自身**的长度（`19` / `21` … 就是目标路径字符串的字节数）。

⇒ 两处要改：`kindLabel` 要看 `isSymlink`（`LocalEntry` 已经有这个字段，只是没用它），
且**符号链接不该显示自身大小**（显示 `—` 或目标）。

⚠️ 这条与 `places()` 的过滤是**两件事**：`places()` 管的是**弹窗里列不列它**，
而 F2 管的是**在列表里长什么样**。因为 F1（开局在容器里），列表里**一定会看到这五项** ——
所以 F2 不是理论问题。

## F3（新发现）列目录**穿过容器符号链接会失败** —— 换个 API 就通

同一个目录，两种列法结果相反（2026-10-12 实测）：

| 列法 | 结果 |
| --- | --- |
| 探针用 `contentsOfDirectory(atPath: "<容器>/Downloads")`（路径版） | ✅ 8 项 |
| app 用 `contentsOfDirectory(at: <容器>/Downloads, includingPropertiesForKeys:)`（URL 版） | ❌ `NSFileReadNoPermissionError` |
| app 用**解析后**的真实路径 `/Users/tango/Downloads` | ✅ 6 项（就是上面那张图） |

⇒ **URL 版 + 预取子项属性这一步，在穿过容器符号链接时会被拒。**
教训不只是「要解析符号链接」，更是：**「探针能列」不等于「app 也能列」—— 两者 API 不同，
结论就不通用。** 已记进 `1011_05` 的「别做」清单。

## 沙盒版现在**能访问什么**（用户直接问的问题）

| 位置 | 能读吗 | 判据 |
| --- | --- | --- |
| 真实 `~/Downloads` | ✅ 能 | app 里列出 6 项真实文件 |
| 真实家目录 `~` 本身 | ❌ 不能 | 按「向上」：`未能打开文件"tango"，因为你没有查看它的权限。` |
| `~/Desktop` / `~/Movies` / `~/Pictures` / `~/Music` | ❌ 不能 | 探针实测 `errno 257` |
| `~/Documents` | ❌ 读不到真实那份（容器里那个是空的） | 探针实测 |
| `/` | 能列，但只剩 4 项 | app 实测 | 
| 照片图库 | ✅ 有 PhotoKit 权限（**未跑过真实相册**） | entitlements |
| 任意素材目录 | ✅ 但**必须用户亲手选一次**（`NSOpenPanel` + bookmark） | 待实现 = E7 |

⇒ 这正是「用户的视频、照片不止在 Documents 中」的答案：**entitlement 永远覆盖不了一堆分散的素材目录，
只有「选一次 + 记住 bookmark」能。E7 是产品能力，不是合规装饰。**

## 反例：一条**我读错、被机器纠正**的结论

第一次看截图时我把底部读成「3 个项目」——而列表里有 9 行，看着像个「状态栏数字不对」的真 bug。
用 UI 树一读：**「9 个项目」/「13 个项目」**，与行数完全一致。

**是我在缩小后的位图里把 `9`/`13` 看成了 `3`。** 记在这里有两个原因：

1. 它说明**数数这类判据要交给 UI 树**，不要靠读图 —— 截图适合看「长什么样」，不适合数「有几个」；
2. 它是一条**差点被写进验收报告的假缺陷**。差一步就是「拿一条自己看错的结论去让人改代码」。
